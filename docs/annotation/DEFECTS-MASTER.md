# 缺陷总表（DEFECTS-MASTER）

> 只记「会让闸假通过」的缺陷，一条一节：现象 / 为什么假通过 / 修复判据 / 正负对照。
> 每条必须能指到判据文件的具体字段，不接受「已注意」这类结论。

## D-001 计划行「平移」假通过（b350 修）

- **现象**：计划 112/113/114，实际写 113/114/115，且 115 也在计划集内 → `numstat=28/28`、
  `out_of_scope_edits=0`，`scope` 与 `commit` 两闸全过，但 112 从未被写。
- **为什么假通过**：`numstat == plan` 只比**行数**；`out_of_scope_edits` 只看**每一行是否在计划集内**。
  两者都不检查「计划集是否被逐行覆盖」，整体平移时两边同时成立。
- **修复判据**：`precheck-assert --scope` 新增 `plan_lines_covered=X/Y`，
  X = 计划行中被**新增注释行**命中数；`X < Y` 即 `exit 1`，`gate-run` 的 `scope` 闸把该字段列为必现。
- **正负对照**（b350 实测）：
  - 负控（纯平移、越界 0）：`plan=23 diff_new=20 out_of_scope_edits=0 plan_lines_covered=20/23` → **exit 1**，
    逐条报 `SettingsPage.tsx:1458/:1641/:2375 未改动`。
  - 正控（b349 真实批次，`--base d14f8641^`）：`plan_lines_covered=20/20` → **exit 0**。

## D-002 「删行也算已覆盖」（b350 修）

- **现象**：旧实现把「计划行是否出现在 diff」按 **旧行 ∪ 新行** 判定。某行只被**删除**（未补新注释）时，
  它仍算「改到了」，`missing` 为空，闸放行。
- **为什么假通过**：覆盖率的分母是「计划行」，分子却取「被触碰的行」。删除动作本身就是触碰，
  于是「把注释删掉但不重写」不会被判漏改——这与 D-001 的平移是两类不同的假通过，不能合并计一条。
- **修复判据**：覆盖集合改为**仅 `newLines`**（新增注释行）：`covered = new Set(newLines.map(keyOf))`。
  删除不再产生覆盖。
- **正负对照**：同 D-001 两组；另测「零改动」（`--base HEAD`、工作树干净）→
  `plan_lines_covered=0/32`、**exit 1**，而旧实现此时也是 0，说明新旧在「完全没动」上一致，
  差异只在「删了但没写」这一类，需靠 b350 起的真实批次持续核对。

## D-003 计划外改动（改错行）是否被 `--scope` 拦住 —— 负控实测（b362 前，结论：能拦）

- **背景**：b361 我把计划行 84 按文本匹配改成了 66，靠 `judge-generic` 发现，当时没跑 `--scope`。
  「按实现应为 24/25 + exit 1」只是推断，故构造负控实测。
- **负控构造**：`ToolPresentation.tsx` 计划只含第 84 行；实际只改第 66 行（66 不在计划集）。
- **实测输出**：
  ```
  PRECHECK SCOPE plan=1 allow=0 diff_old=1 diff_new=1 out_of_scope_edits=1 plan_lines_covered=0/1
  SCOPE OUT old ...:66   // 只有存在规整能力时才改写输出。
  SCOPE OUT new ...:66   // 只有存在规整能力时才改写输出。
  SCOPE MISSING ...:84（plan 登记但未改动）
  PRECHECK SCOPE FAIL 越界 1 行 / 漏改 1 行（plan_lines_covered=0/1）
  ```
  **退出码 1**；`out_of_scope_edits=1`，不是 `25/25` 通过。
- **正控**：b361 真实批次 `plan=25 allow=0 diff_old=25 diff_new=25 out_of_scope_edits=0 plan_lines_covered=25/25` → exit 0。
- **结论**：这道闸**能**拦住「计划外改动 + 漏改」，且是**双计数**（越界行 + 漏改行），
  与 D-001（行数相等、平移后仍全覆盖）、D-002（删行即算覆盖）都不是同一类。
  **三处必须写清**：
  1. **与 D-001 / D-002 的区别不在判据，在「闸没跑」** —— 那两条是闸跑了但判据错（假通过）；
     D-003 是判据本身正确、只是没人调用它。因此处置是流程项（§6.2 第 20 条），不是改判据。
  2. **正负对照都要留**：正控 = b361 真实批次 `25/25` → exit 0；负控 = `0/1` → exit 1，且同时报越界 1 行 + 漏改 1 行。
  3. **注释是事故的放大器**：源码头注释原写「`--scope` 只报不拦（永远 exit 0）」，
     与实现相反——**没跑过这道闸的人会因此认为跑了也没用**，从而不去跑。已订正为「检出越界/漏改即 exit 1」。

## D-004 工具顺序：`pick-generic` 必须在落笔之前调用（b366 修）

- **与 D-003 同族**：工具在、判据对，错在**调用时机**。D-003 是「闸没跑」，D-004 是「工具跑了但跑在错误的状态上」。
- **症状**：b366 先落笔、后跑 `pick-generic`，输出 `TALLY {"pending":31,...} plan=0` —— 一行计划都没有，
  但脚本 exit 0、没有报错，只靠人看 `plan=0` 才发现。若直接跳过，六闸的 `plan=0` 会让 scope 变成「0 行全覆盖」，
  是 D-001 那类假通过的入口。
- **根因**：`pick-generic` 用 `git blame` 取归属；工作树已改的行，blame 返回全 0 sha（`0000…0`），
  脚本把它计入 `pending` 并 `continue`，于是整批落 pending、计划为空。
- **三行最小正控（b366 实测，可复跑；`pending` 两个口径别混读）**：
  1. 已改行上 blame 返回全 0 sha：
     `git blame --porcelain -L 104,104 -- packages/ui/src/previewPaneCodeContent.tsx | head -1`
     → `0000000000000000000000000000000000000000 104 104 1`
  2. **最小复现规模**（先改 1 行再 pick）→ `TALLY {"pending":1,...} plan=0`；
  3. **正确顺序**（`stash push -- <files>` → pick → `stash pop`）→ `TALLY {"ownIn":1,"pending":0} plan=1`。
- **原批规模（b366 首跑）是 `pending=31` / `plan=0`**：31 是本批计划行总数，不是控制组的规模。
  两个数分别代表「最小复现」与「原批规模」，不是前后矛盾的两次观测。
- **处置**：落笔顺序固定为 `--start` → **`pick-generic`** → 起草落笔 → `plan-new` → precheck → 等集断言 → judge → 六闸
  （INDEX §6.2 第 16 条）。若已经先改了，用 `stash push -- <6 文件>` → pick → `stash pop` 复原，不要手工补 plan。
- **不修脚本的理由**：脚本改成「读 HEAD 版 blame」会掩盖「工作树有未计划改动」这一事实；
  顺序约束比隐式容错更能保证「计划先于落笔」。
