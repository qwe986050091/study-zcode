## 1. 池的唯一权威计数器

### 1.1 49 是什么（实测，不再靠推）

```text
node deep-quality.mjs <clean worktree> --root docs/knip --list-weak
WEAK lines=49 files=4
```

| 文件 | 行数 |
| --- | ---: |
| `docs/knip/docs/scripts/generate-plugin-docs.ts` | 16 |
| `docs/knip/docs/scripts/get-monthly-sponsorships-opencollective.ts` | 13 |
| `docs/knip/docs/src/util/post.ts` | 12 |
| `docs/knip/docs/scripts/get-monthly-sponsorships-github.ts` | 8 |
| 合计 | **49** |

三项定性：

1. **不是记账差**：这 49 行在基线 tsv 里没有单独登记（基线只覆盖 `packages,apps` 的 1,007 文件 / 7,421 行），
   但它们是 `git diff -U0 8f7daaf0 HEAD` 的 `+` 行，按池定义**必须计入**池内 weak。
2. **不是池外连带**：池的判定只看「`+` 行 ∩ 当前 weak」，与文件属于哪个包无关；`docs/knip` 一样进池。
3. **是扫描域漏项**：`6,476` 由 `--root packages,apps` 得到，少扫了 `docs/knip`，于是 `6,476 + 49 = 6,525`。
   换句话说，`6,525` 才是全池，`6,476` 是它的子集投影。

### 1.2 定稿：唯一权威计数器

| 角色 | 口径 | 值（b264 后） | b265 后 | 用途 |
| --- | --- | ---: | ---: | --- |
| **权威** | `deep-quality --root packages,apps,docs/knip --list-weak` ∩ 池 | **6,425** | **6,325** | **收口只按它判「清零」** |
| 参考 | `--root packages,apps`（同池，漏扫 `docs/knip`） | 6,376 | 6,276 | 只作对照，**不可与权威数相减** |
| 参考（历史） | b261–b264 四时点 `8acd208e/0cab755e/e3116a93/2e779933` | 6,776 / 6,676 / 6,576 / 6,476 | — | 旧快照，仅供复算 |

**收口判据**：`ACCT lines remain == 0`，其中 `remain` 由权威口径实测，且 `acct_remain == pool_remain` 必须成立。
不再接受「目标是 0 还是 49」这种问法——目标是 0，49 已经含在里面。

## 2. 计划表三列：真上游 / 本线已转强 / 可写

`upstream=7` 是把两类完全不同的行塞进一列：**真上游**（写不了）与**本线已转强**（不用写）。
`100 + 7 = 107` 算术没错，但它把「配额分母」和「已完成量」混在一起，所以计划表从本批起按三列写。

| 本线已转强（块尾 `*/`） | **3** | `node-repl-session.ts:142`、`SaveWorkflowPermissionBlock.tsx:51`、`SaveWorkflowPermissionBlock.tsx:152` |

### 2.2 b265（本批）的 112 拆解

| 类别 | 行数 | 说明 |
| --- | ---: | --- |
| 真上游（池内） | **0** | 池 = `+` 行，上游行进不来 |
| 本线已转强（池内块尾 `*/`） | **0** | 本批自清只有 1 条，且在池外（§4.3） |

| 合计 weak | **112** | `100 + 12` |

三态脚本输出（`b265-pick.txt`）：

```text

```

### 2.3 为什么三列不能并

- 并成一列（`upstream`）时，`writable` 与「已完成」会互相抵消：b264 的 3 条块尾 `*/` 是**改前 weak、改后不 weak**，
  它们既不该进配额，也不该算作「写了 3 行」。
- 池外 12 行同理：它们不进 ACCT、不进池、也不进配额，但**会出现在 `--list-weak` 里**，
  不单列就会把「112 → 11」误读成「清了 101 行配额」（实际清了 100 行配额 + 1 行池外）。
- 因此计划表固定三列 + 一行「池外另计」，且 `quota` 一律由 `writable − self-clearing(可写桶)` 得（§4）。

## 3. `uncovered` 的定义与序列

### 3.1 定义

`deep-quality.mjs --uncovered <out>` 输出**代码单元未覆盖明细**，一行一条 `<path>\t<line>\t<B|->\t<正文>`：

- **unit**：非空、非注释、非结构行（`{`/`}`/`)` 等）、非 import、非续行的代码行；
- **covered**：该 unit 上方 2 行内有整行注释，或本行有行尾注释；
- **uncovered**：不满足 covered 的 unit（`B` 表示分支/块）。

一句话定义：**`uncovered` = 当批文件集内、上方 2 行内没有任何整行注释的代码单元数**。
PLAN#2 只改写既有 weak 注释（1→1 换正文），**不新增注释行**，所以它在每批**构造性不变**——
这不是「量出来恰好不变」，而是「不改变输入就不可能变」。

### 3.2 作用域

由 `--root` / `--file-list` 决定，**本工程一律是「当批那几个文件」**，不是全仓。
所以它跨批不可比（文件集与 unit 总量都变），只能批内比。

### 3.3 四批「规划时值 / 批后值」

| 批次 | 文件 | 规划时值 | 批后值 | 差 | 性质 |
| --- | ---: | ---: | ---: | ---: | --- |
| b262 | 5 | 428 | 428 | 0 | 预期不变，**非进度指标** |
| b263 | 5 | 877 | 877 | 0 | 预期不变，**非进度指标** |
| b264 | 5 | 649 | 649 | 0 | 预期不变，**非进度指标** |
| b265 | 5 | **4,911** | **4,911** | **0**（`Compare-Object` 差 0 行） | 预期不变，**非进度指标** |

`b265` 的 4,911 明显高于前几批，只因为本批含 `botsService.ts`（5,434 units，占本批 6,679 units 的 81%），
不是质量退步——同一批内的 pre/post 完全一致。

### 3.4 结论：**不改名**，它是「后测指标」而不是「规划快照」

- 它在批次**开始时与结束时各测一次**，两次都量当前工作树的真实状态；b265 的规划时值就是 4,911，不是从上一批继承的 649。
- 1→1 改写只换注释**正文**，既不增删注释行（门禁 `删本线注释 100` 与 `新增注释行 100` 等量），也不动代码行
  （`删代码 0`、`新增非注释行 0`），unit 集合与 covered 判定都不变，所以**构造性恒等**。
- `877 → 649` 这种批间跳变是**文件集变化**（b263 的 5 文件 unit 总量 1,066，b264 的是 721），不是进度。
- 它测的是「这些文件里还有多少代码行没注释」，而收口标准是「池内 weak 清零」（`--list-weak`），两者正交。
  因此台账把它记为**非进度指标**，不参与任何进度/产能判断；名字保持 `uncovered`，避免用 `_at_plan` 暗示它是排期输入。

### 3.5 收口边界：池清零 ≠ 全仓完成

- 池内 `6,325` 清零 **不等于 ZCode 全仓注释完成**。
- 同一批文件集内仍有 **4,911** 个「上方无整行注释」的代码单元（b265 实测），属**未承诺范围**：
  PLAN#2 只改写既有 weak，不新增注释，工程从未把补齐它们写进配额。
- **禁令**（与 `INDEX.md` §2.4 的用法禁令同级）：**禁止用「池清零」「remain=0」暗示或表述「全仓注释已完成」**。
  对外只能写「PLAN#2 池内 weak 清零」或「注释清水工程阶段性收口」，并同时给出本节 4,911 这个未承诺量与它的作用域
  （当批文件集，不是全仓）。域外的注释密度从未被本工程测量，也没被承诺。

## 4. `self-clearing`：配额 = `writable − self-clearing`

### 4.1 实现

`capacity-estimate.mjs` 新增 `--pre-weak <本批改写前的 --list-weak 快照>`：

```text
selfClearing = preWeak − 现weak − 本批登记表(rewritten)
```

即「改前 weak、改后不 weak、且台账里没有这一行」——没落笔却转强，典型成因是块尾 `*/`：
句元向下合并时它跟着前一行判弱，前一行写强后它自动转强。

输出（四桶，只有可写桶进扣减）：

```text
SELF-CLEAR n=1	可写桶 0 / 池外 1 / 上游桶 0 / 未解析 0	（只有可写桶进配额扣减）
  apps/zcode-cli/packages/core/src/tool/handlers/agent.ts:225	bce5596a	out-of-pool
```

`PLAN` 行：

```text
PLAN#1	5 文件 / 100 行	writable=100 self-clearing=0 upstream=0 pending=0 quota=100	…
PLAN#2	5 文件 / 100 行	writable=100 self-clearing=0 upstream=0 pending=0 quota=100	…
```

### 4.2 b264 的 3 条：上游桶（不扣）

`node-repl-session.ts:142`、`SaveWorkflowPermissionBlock.tsx:51/:152` 的 blame 不在白名单，
本来就不进 `writable`，扣它会重复计数。

### 4.3 b265 的 1 条：池外桶（本轮补的第四桶，修法说明）

`agent.ts:225` 是 JSDoc 块尾 `*/`，blame `bce5596a` 在白名单内 → 首版实现会归进「可写桶」。
但它**不在池内**（`git diff -U0 8f7daaf0 HEAD` 的 `+` 行集合里没有 225，实测 `pool_has_225=false`，`pool_has_226=true`），
所以它既不在 ACCT 也不在池，扣配额会得出「配额 99、实际清 100 行」的矛盾。

修法：分类顺序改为 **池外 → 未解析 → 可写 → 上游**，并打印 `池外 N`。这也让「可写桶」的定义与
`triState` 完全一致（池内 + 白名单），不再有两套口径。

### 4.4 b264「配额恰好等于可写」不是巧合

b264 的 `PLAN#1` 打印 `writable=100 self-clearing=0 quota=100`：

- 可写桶里**没有**自清行（3 条自清全在上游桶），所以 `100 − 0 = 100`；
- 若那 3 条落在可写桶，配额会变成 97——这正是这一列要拦的「分批后必然差 3 行」的坑。

b265 的账同样对齐：`writable=100`、可写桶自清 0、配额 100、实际清 100 行池内 weak；
另外 1 行池外自清只体现在 `--list-weak` 的 112 → 11（差 101），不体现在 ACCT/pool（差 100）。

### 5.1 新口径：三量并列（b273 起，b274 拆两段墙钟）

| 量 | 定义 | 打点方 | 覆盖 |
| --- | --- | --- | --- |
| `batch_wall_total` | 上一提交 → 本提交（git 时间戳） | git | 整批墙钟：规划 + 改写 + 预检 + 门禁 + 后测 + 提交 + **批间非改写动作**（尺子升级、台账提交） |
| `batch_wall_controllable` | `t-start` → 提交时间 | 工具 + git | 本批可控段：改写 + 预检 + 门禁 + 提交 |
| 落笔段 | `t-start` → `t-verify` | 工具 | 改写 + 预检 + 返修，不含门禁与提交 |
| `tail` | `t-record` → `t-verify` | 工具 | 仅末段：最后一次预检 → verify |

- 四量并列报，缺一不影响其他；`--order` 另做顺序断言 `t-start < t-record ≤ t-verify < commit_time`。
- **`total` 不得除以行数当改写成本**：b273 的 `943.0s` 含批间尺子升级 `b8843802`，与 `controllable=195.0s` 差 748s。
- 旧表的 `s/行` **不换算**进新口径：起点、终点、打点人都变了，换算只会产生新的人工打点。
- 新口径主档：等 `batch_wall_controllable / 100` 的同段样本攒到 n=5 再定；当前 n=1（b273）。

**剩余 6,325 行排期（旧口径，中位数 2.17，b273 起停止使用）**：

## 9. 收口标准（可判定断言，替掉「池清零」这种自然语言）

「收口」只有三条**同时成立**才算，缺一条都不许写「已完成」：

| # | 断言 | 判定方式 | 当前值（b265 后） |
| --- | --- | --- | --- |
| A1 | 池内剩余 = 0 | `capacity-estimate.mjs` 输出 `REMAIN … 0 …` | 6,325（未达成） |
| A2 | 记账恒等 `done + remain == 7,421` | 同件输出 `ACCT lines done X + remain Y = 7,421 OK` | 1,096 + 6,325 = 7,421 OK |
| A3 | 台账自检通过 | `ledger-assert.mjs` `exit 0` 且 `ASSERT PASS` | PASS |

A1 与 A2 由同一次 `capacity-estimate` 运行产出（`ALIGNED acct_remain == pool_remain` 是 A2 的伴随断言，
不等即 `exit 1`）；A3 与 A1/A2 互不替代：前者校台账（802 等式、`--uncovered` 清单、豁免项），后者校池账。

**`7,421` 这个域怎么来的**：`packages`、`apps`、`docs/knip` **三个根**下全部文件在基线
`weak-own-by-file.tsv` 里的 weak 行并集 = **7,421 行 / 1,007 文件**，它就是「待清零的池」的全量分母。
因此：

- `7,421` 与 `6,325`（以及 `6,425`、`6,525`）只在**这个域**内可比；
- 域一变（加减根、加减排除项、换基线快照 `8f7daaf0`），两个数都不可比，必须重算基线并显式标注新域；
- 参考口径 `6,476` 系列是 `packages,apps` 两根投影，**不属于本域**，不能与 `7,421 / 6,325` 相减（§1.3）。

判定顺序固定：`A2`（账是否自洽）→ `A1`（是否归零）→ `A3`（台账是否如实）。A2 失败时 A1 的 0 不算数——
那说明分母被换了，不是工程做完了。
