## 0. 为什么要回溯

b283 证明「逐行替换脚本会整行重建」不是假设：它把注释的前导空白与行尾一起改掉，而 `--record` 只比正文字节、
七行门禁只判行分类，两者都看不见。b283 之前没有第 8 行门禁，因此同样的脚本缺陷可能已经发生在更早的批次里，
且不会留下任何报警。这次用**当前版判据**回放 b261–b284 的每一笔改写提交，把「可能」变成可失败的读数。

## 1. 判据与口径

- 对每批的 `提交^..提交` 跑 `git diff -U0`，同一个 hunk 内删除行与新增行**按序配对**（1→1 形状）；
  数量不等说明有插入/删除，交给 `--record` 的集合同构断言，本审计不猜映射。
- 只比**两侧都是注释**的行（`//`、`/*`、`*` 起始）；代码行的格式差异仍由 token 门禁负责。
- 比两个字节序列：前导空白、行尾。任一行任一不等即 `indentChanged` / `eolChanged` +1。
- 两侧都用 `git cat-file --filters <rev>:<file>`：它按工作区属性做 smudge，取到的是「当时工作树应有的形态」。
- `expect_*` 是**已登记的读数**，不是「应该为 0」的猜测；b282 / b283 的修复行以反向读数登记。

没有一行是 JSDoc 的 `*` 续行（不存在「注释块被拆散」），改写后的正文与原来一致，代码行零改动。

修复：`6b765c30`（`fix(注释): b282 缩进/行尾对齐原文（20 行，历史审计回溯）`），

## 5. EOL 列为什么结构性恒 0

每一行都打印 `rawCrlf=0`：`git cat-file -p` 取原始 blob，26 个批次涉及的所有新旧侧都没有 CRLF。
仓库 `core.autocrlf=true`，提交时 LF 写入对象库、检出时 smudge 成 CRLF；`cat-file --filters` 对两侧都做 smudge，
所以「旧侧 CRLF vs 新侧 LF」这种差异在历史里不可能出现。

也就是说，**b282 / b283 当年的 LF 残留只存在于提交前的工作树**，提交动作已把它归一化，历史不可复原。
EOL 列保留是为了证明「查过且确实为 0」，不能解读为「历史批次的行尾都干净」。
可复原的部分另查工作树：b282 三文件的 EOL 残留就是这次这样找到并修掉的。
在线门禁（`--record` / `--verify`）读的是提交前的工作树，因此它拦得住这类问题；历史审计拦不住，这是口径边界。

## 6. 断言本身（可失败性）

- 逐行断言：`indentChanged` / `eolChanged` 与 `expect_*` 不等 → `exit 1`。
- 净额断言：同一批的改写行与 `-fix` 行必须**逐行镜像**（旧空白 == 修复后的新空白，且修复前的空白 == 原旧空白），
  不成立 → `exit 1`。只比数量不够——数量相等但改错了行也会被判红。
- 首跑（登记值为 0 时）：`b282=20`、`b283=12/14` 两处 `exit 1`，`SUMMARY unexpected=2`。
- 补登后复跑：`unexpected=0 result=PASS`。
